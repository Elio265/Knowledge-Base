# 鉴权与 Token 方案

## 一句话理解

认证回答“你是谁”，授权回答“你能做什么”；网关统一登录身份后，通过令牌或签名把身份安全传递给上游，最终授权由数据面策略兜底。

## 核心原理

### Session 与 Token

| 方案 | 状态位置 | 特点 | 问题 |
|---|---|---|---|
| Session | 服务端（内存/Redis） | 可主动失效、踢人 | 需要共享存储；扩容要同步 |
| Token（JWT） | 客户端自包含 | 无状态校验、跨服务 | 无法主动失效；泄露即被盗用 |

- 常见组合：短时访问 Token + 刷新 Token；服务端维护刷新 Token 的可撤销列表。
- JWT 结构：`header.payload.signature`，HS256 用共享密钥，RS256/ES256 用非对称；签名防篡改，**不加密**，敏感信息不能放 payload。
- 失效手段：黑名单、短过期 + 刷新、版本号/代次。

### 网关身份传递

- 网关在登录后把用户身份注入到转发的请求头（如 `X-User-Arn`、`X-User-Name`）。
- 关键安全边界：**必须清洗客户端传入的同名头**，网关自己注入并覆盖，否则客户端可伪造身份。
- 上游仍要按最终策略授权：网关注入身份不等于授权，授权由数据面（如 phxoss Bucket Policy）决定。

### 签名请求（SigV4 类）

- 用密钥对请求要素做 HMAC 签名：方法、路径、query、必要 header、body hash、时间戳。
- 防篡改：任何要素变化导致签名不一致；防重放：时间戳 + 短有效期窗口。
- S3/S3 Express 风格的续列、分片上传等场景依赖这种签名语义。

## 底层实现

- JWT 校验：取公钥/共享密钥 -> 验签名 -> 验 `exp`/`nbf`/`iss`/`aud`。
- SigV4：构造 canonical request -> 字符串待签 -> 派生 signing key -> HMAC -> 签名头。
- 密钥与凭据生命周期：Kerberos 管理 API 用 RSA 密文提交管理员密码、数据库可逆加密保存、查询返回占位符；但 `kadmin -w` 会出现在进程 argv 与远端日志中，脱敏不完整（见 [[Kerberos域接入与用户映射管控]]）。
- Python 注意：字符串不可原地清零，密码/密钥会残留在内存、参数与日志中，要避免把密钥拼进 URL/异常。

## 常见应用场景

- [[SangBridge AI统一接入与管理控制台]]：登录后 FastAPI 网关 `Depends(get_identity)` 取身份，通过 `X-User-Arn` 与用户凭据签名向 phxoss 转发；前端权限治理（按钮置灰、请求前校验）只负责体验与防误操作，最终安全边界是 phxoss Bucket Policy。
- 平台既有能力边界：Token、WAF、审计、SigV4/S3 Express 属于产品已有能力，本人未核验为个人成果，但面试被追问时要能讲清原理与边界。

## 容易踩坑的地方

- 把前端权限当安全边界：直接构造 HTTP 请求即可绕过，必须由服务端/数据面授权兜底。
- Token 存 localStorage：XSS 直接拿 Token；httpOnly Cookie 更安全但要处理 CSRF。
- 密钥硬编码、日志打印、错误信息回显密钥内容。
- JWT 没有主动失效：删除用户/改权限后旧 Token 仍有效，需要短过期或黑名单。
- 只验签名不验 `iss/aud`：Token 可在别的服务复用。
- 时间戳窗口过大导致重放窗口大，过小导致时钟偏移误杀。
