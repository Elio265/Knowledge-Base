# 后端接口设计与分页

## 一句话理解

接口设计本质是定义稳定、可演进、语义清晰的契约；分页选型由数据规模与一致性要求决定，深分页和翻页不重不漏是核心考点。

## 核心原理

### 分页模型对比

| 模型 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| offset/limit | 跳过前 N 条再取 M 条 | 实现简单、可跳页 | 深分页慢（越翻越深）；写入并发下重复/丢失 |
| keyset / cursor | 用唯一有序键定位（`id > last_id` 或 `(created_at, id)` 复合） | 稳定、可走索引、翻页快 | 不能跳页；键必须唯一稳定 |
| opaque cursor（不透明 token） | 服务端把游标编码/加密后返回，客户端原样透传 | 语义可演进、服务端可控 | 需要服务端管理游标状态/失效 |

### 契约原则

- 响应携带 `truncated`/`has_more` 与 `after`/`next_cursor`，**前端以后端标记为准**，不能按“本次返回条数是否等于页大小”猜下一页。
- 搜索、筛选、排序变化或刷新时，旧游标必须重置/作废。
- 列表接口要定义排序稳定性：没有稳定排序就没有稳定分页。

### 错误与稳定性

- 统一错误结构（错误码 + 消息 + 可重试标记），网关把上游错误转换成对外契约（[[SangBridge AI统一接入与管理控制台]] 的错误转换职责）。
- 写接口考虑幂等键；读接口考虑缓存与失效。
- 限流：网关层按用户/接口维度控制，返回明确限流错误，避免打爆上游。

## 底层实现

- keyset SQL：`WHERE (created_at, id) > (?, ?) ORDER BY created_at, id LIMIT n`，利用复合索引避免深翻页扫描。
- offset 翻页到深处会全表扫描，页越大越慢。
- S3 ListObjectsV2 用 continuation token 续列，token 由服务端生成，**不能用文件名等业务字段替代**。
- 并发写入场景：基于事务快照的游标能保证单次翻页内一致，多页之间仍可能看到新增数据，属于正常语义，需和产品对齐。

## 常见应用场景

- [[SangBridge AI统一接入与管理控制台]] 的游标分页治理：
  - 仓库列表：`limit/after`，优先使用上游 opaque `after`，缺失时才回退最后 `bucket_name`。
  - 分支/标签：以后端 `truncated` 决定是否存在下一页。
  - 提交图：`after` 是不透明游标，加载更多应透传、追加。
  - S3 快照文件树：必须用 continuation token，不能把文件名当 token。
  - 前端统一 `useCursorPagination`：末页修正、失败清空、乱序丢弃旧响应、重置清空游标。

## 容易踩坑的地方

- exact-page 假下一页：返回条数等于页大小就显示“下一页”，实际已到末页。
- 把“最后一项的某个字段”当成通用游标：字段不唯一或不稳定时翻页重/漏。
- 搜索或排序变化后继续用旧游标：结果集变了，游标失效。
- 前端并发请求乱序返回：旧响应覆盖新数据，需要丢弃过期响应。
- 游标编码：Base64 要 URL-safe，避免 `+`、`/`、`=` 被解析破坏。
